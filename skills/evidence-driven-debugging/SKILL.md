# Evidence Driven Debugging

복합적이거나 반복되는 기술 실패에서 관찰과 가정을 분리하고, 다음 행동을 바꾸는 판별 근거로 근본 원인을 좁힌다. 일반 구현 규율이나 모든 버그 수정 절차로 확대하지 않는다.

## 적용 조건

다음 중 하나 이상이 분명할 때 사용한다.

- 첫 수정이 실패했거나 같은 증상이 재발했다.
- 서로 다른 원인 후보가 둘 이상 합리적이다.
- 회귀 인과가 불명확하거나 기준선에도 같은 결함이 있을 수 있다.
- 코드, 입력 데이터, 설정, 환경, 측정 방식, 계약을 혼동할 가능성이 있다.
- 사용자가 근거 기반 근본 원인 진단을 명시적으로 요청한다.

다음에는 사용하지 않는다.

- 원인과 수정이 명백한 작은 단일 결함
- 일반 구현, 리팩터링, 코드 리뷰, 상태 확인
- Codex 규칙·정책·사용자 선호의 출처와 우선순위 추적. 이 경우 `codex-why`를 사용한다.
- 근거 없이 가능한 원인을 많이 나열하는 브레인스토밍

진단·검토 요청은 읽기 전용으로 유지한다. 사용자가 수정이나 복구도 요청한 경우에만 상태를 변경한다.

## 진단 절차

1. 관찰된 증상, 기대 동작, 비교 기준선, 가장 작은 재현 또는 직접 관측을 고정한다.
2. 확인된 사실과 아직 검증하지 않은 가정을 분리한다.
3. 관련 있는 원인 범주만 분류한다.
   - 코드
   - 데이터 또는 입력
   - 설정
   - 환경 또는 도구 체인
   - 측정 또는 평가 방식
   - 제품·프로젝트의 동작 계약 또는 authority
   - 외부 의존성
4. 현재 근거로 가능한 가설만 남긴다. 각 가설에는 결과에 따라 다음 행동이 달라지는 가장 저렴한 판별 관측을 하나 연결한다.
5. 읽기 전용 관측을 우선하고 한 번에 한 인과 요소만 바꾼다. 입력과 환경이 변하지 않았다면 검증된 근거를 재사용한다.
6. 확인된 원인, 결과에 중요한 배제 원인, 남은 미지수를 구분한다. 근거가 가설을 구별하지 못하면 추측성 패치를 하지 않고 `UNKNOWN`으로 멈춘다.
7. 수정이 승인되고 근본 원인이 지지될 때만 가장 작은 근본 수정을 적용한다. 포착된 실패 경로와 직접 영향받는 회귀를 검증한다.

검증 형식은 문제에 맞춘다. 실제 사용자 진입점, 작은 probe, smoke test, 시각 확인 또는 관련 테스트를 선택하며 고정된 테스트 개수나 진단 일지를 만들지 않는다.

## 다른 스킬과의 경계

아래 스킬은 설치된 경우에만 선택적으로 연계한다. 없으면 현재 스킬의 진단 절차와 적용 지침을 따른다.

- 원인이 확정된 뒤의 최소 실행과 검증은 `execute-leanly`가 맡을 수 있다.
- `swarm`이 적용되더라도 원인과 계약이 고정되기 전 진단은 Main이 소유한다. 이 스킬은 직접 위임하지 않는다.
- Codex 정책·규칙·선호의 provenance는 `codex-why`가 소유한다.
- 승인된 과거 기록은 이전 실패와 검증된 우회가 현재 조건에 맞는지 확인할 때만 선택적으로 사용한다. 이 스킬 자체는 기록을 저장하지 않는다.

## 결과 형식

필요한 항목만 간결하게 보고한다.

- 관찰된 실패
- 확인된 원인과 결정적 근거
- 결과에 중요한 배제 원인
- 승인된 경우 수정과 검증 결과
- 남은 미지수

## 부작용 금지

- 진단 로그, 원장, 계획 파일, 새 gate를 만들지 않는다.
- 기억을 쓰거나 수정하지 않는다.
- 새 task, fork, subagent를 만들지 않는다.
- 사용자가 요청하지 않은 수정·외부 동작·범위 확장을 하지 않는다.
- 현재 원인과 승인된 수정이 검증되면 종료한다. 무관한 발견은 현재 사용에 실질적 영향이 있을 때만 미처리 상태로 보고한다.
