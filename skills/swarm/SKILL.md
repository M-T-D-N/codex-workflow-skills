# Swarm

Reduce Main's investigation, implementation, and rework while preserving required outcomes and verification. Use the implementation roles below and preserve Local Qwen as an opportunistic local worker for naturally independent, low-risk work with cheap verification. Do not create work, fragment a coherent task, or count calls as savings.

This portable edition supplies instructions, not a worker runtime, model weights, or executable adapter. Read [worker setup](references/worker-setup.md) when the current environment does not establish an authorized worker contract. Use the selected model and effort only when the host exposes them; otherwise Main owns the unit. Never invent model identifiers, executable paths, or substitute-model cascades.

## Preserve authority

- Keep the user's Main model and reasoning effort unchanged. Main owns scope, approvals, consequential meaning, integration, and the final answer.
- Inherit repository, sandbox, external-data, and scheduling boundaries. This skill requests eligible delegation; it cannot override the available tool's conditions or grant new permissions.
- Use one owner per unit, one active writer per repository or worktree, and no nested delegation or competing implementation. Tests sharing mutable outputs also conflict.
- Track the exact worker invocation or native handle. Before transferring ownership, confirm its execution ended and attribute changes against the starting state. Completion of a turn does not prove disposal of an agent or release of a slot. Classify each result once as accepted or discarded.

## Choose the next owner before solving the unit

Use the first targeted reads already needed for the request. Consider the whole request first, then natural independently checkable units. Do not run a repository survey, mapper, scoring system, or routing log just to find delegation.

1. **Use an existing tool** when a verified command or converter already completes the work. Main handles genuinely trivial edits whose handoff and review would dominate.
2. **Keep unresolved meaning with Main.** Main decides architecture/shared-core contracts, security, permissions, migration, deployment, possible data loss, temporal/concurrency semantics, novel algorithms, formal/global claims, and material evidence conflicts. Keep inseparably coupled implementation or work without a reliable way to judge its outcome with Main. Apply this boundary to the unit, not the whole task: Main may retain deletion, publishing, policy adoption or GUI control while a worker inspects fixed files, traces or source behavior. Conflicting writes or use of the same mutable device/test state remain serialized.
3. **Hand off ready work.** The required outcome and bounded ownership must be clear, necessary inputs/tools accessible, acceptance independently checkable, and enough work remain to justify handoff plus review. Main may resolve the missing requirement, root cause, or acceptance example, but stops before deriving the patch. Routine internal design and finding the project's relevant test command belong to a capable native worker.
4. **Choose the suitable worker directly.** Local Qwen may handle a naturally separable unit when its scope and expected output are clear, verification is cheap, failure has low impact, and dispatch/startup/review cost is small. Bounded reading, evidence extraction, structuring or classification, and small changes with settled requirements are examples, not an allowlist or file-count rule. Keep explicitly owned paths and the existing adapter's supported formats/tools. If suitability is unclear, or the work needs substantial interpretation, long autonomous execution, repeated strategic adaptation, consequential final review, or near-complete rework by Main, choose the suitable implementation worker or Main. For independent implementation with clear acceptance, prefer `gpt-6.1-sol`. Use `gpt-6-luna` for a narrow implementation, format conversion, fixture/test branch or bounded evidence unit whose result is cheap to verify. Select reasoning effort for the ready unit using the guidance below. Main retains consequential contracts and final integration. These are defaults unless the user explicitly selects a worker model or effort; they are workload choices, not universal model rankings or automatic global routing. A worker need not first fail another model.
5. **Distinguish suitability from availability.** A disabled service, model/capacity limit, approval, or a host rule requiring independent parallel work is an execution condition. Do not disguise it as unsuitable work or bypass it. Main owns a unit that cannot be delegated safely, with one concrete reason.

### Worker reasoning effort

Choose the model for the work's required capability first, then its reasoning effort. Keep Main's selected model and effort unchanged. These are local starting points informed by [official subagent guidance](https://learn.chatgpt.com/docs/agent-configuration/subagents) and [model guidance](https://learn.chatgpt.com/docs/models), checked on 2026-09-30; they are not proven equivalence between models.

- Honor an explicit user worker model/effort. Otherwise start Sol and Luna at `high`, and adjust for the unit's planning, interactions, edge cases and acceptance evidence.
- Use `low` for straightforward lookup, extraction or transformation, or `medium` for settled implementation with few interactions, when a direct inexpensive check establishes the result. Delegation must still replace useful work; do not create a worker for a trivial command.
- Keep `high` when tracing logic, integrating several steps or checking assumptions and edge cases. Choose `xhigh` when substantial planning or dense dependencies need deeper reasoning; reserve `max` for especially difficult ready units where extra depth justifies latency and usage. Parent-task risk, file count or elapsed time alone does not select the effort.
- More effort does not settle consequential meaning or expand permissions. Resolve those decisions with Main before dispatch. If a unit exceeds Luna's focused role, choose Sol or Main rather than assuming Luna at `max` supplies the missing capability.
- Pass the selected pair explicitly through the supported native arguments and include its brief workload rationale in the existing handoff. Use only efforts supported by that model and tool; no silent replacement. A change requires a supported override or compatible/new worker after ownership is reconciled. Do not use an automatic low-to-max retry ladder or promote permissions, approval or tool failures as reasoning failures.

Make the Qwen choice within Main's existing planning; the user need not mention Qwen. Do not add a classifier/model call, search for work to offload, a per-turn health probe, Qwen-specific summary, or mandatory critic. Perform the existing execution preflight only when actually dispatching Qwen. If handoff plus verification would cost more work than it replaces, keep the existing path.

At an existing work boundary—failure cases become concrete, a prerequisite or meaning is resolved, or an accepted result is integrated—apply the owner choice above to the next necessary unit before Main investigates it or designs its patch. Include read-only comparison and verification, even when no code change is planned. An earlier worker assignment does not cover newly ready work; assign a worthwhile independent unit through the supported lane, including later in the same Main turn. Reuse unchanged decisions; do not add periodic checks, search for extra work, or relabel a failed objective as a new unit.

### Bounded evidence collection

Luna may answer a concrete multi-file question, locate relevant callers/tests, extract specified facts, or classify bounded logs when handoff has useful work to replace. It returns inspected scope, exact file/line or source references, findings, and gaps; a diff is not required. Main retains interpretation of the user's request and consequential conclusions. A failed or limited search does not prove global absence. Do not spawn a researcher for a one-command lookup or open-ended exploration. Qwen may also collect bounded evidence when the selection conditions above fit and the existing read-only adapter can access it. Require source references and an inexpensive source/schema check; a write diff or invented test command is not required. Main owns consequential final criticism and integration; use independent evidence only when useful.

## Local Qwen execution and lifecycle

Select an eligible unit under the opportunistic conditions above before any Qwen-specific state check or startup. Use the verified local adapter and lifecycle described in [worker setup](references/worker-setup.md). This distribution includes no Qwen executable or control-plane script. Select an eligible unit before starting a service. An off service alone is not a reason to reject it when the configured, authorized entrypoint can start it and verify its exact model, context, and readiness.

Optional prewarm may overlap necessary preparation only through that documented lifecycle; join readiness before dispatch and retain the returned instance identity. Do not prewarm excluded work or retry a failed prewarm through another path.

Invoke the configured public operation once per frozen unit with its actual supported workspace, request, source/owned-path and acceptance inputs. For read-only work, use its documented read-only mode, identify the requested output and source/schema check, and omit an executable acceptance command when none is needed. Read-only work must not run mutating tests. Its contract must establish resource ownership, readiness, and accessible worker results, including on nonzero exit. Do not bypass its control plane with a lower-level worker script. Retain the service instance and whether this task started it, including prewarm ownership.

For writes, accept only a well-formed adapter `DONE` (or a documented equivalent completion state), the intended diff within explicitly owned paths, only required test/fixture changes, no weakened or unrelated tests, current acceptance exit `0`, and Main's semantic check. For read-only work, require `DONE`, no changed files, complete requested output with source references, and the specified cheap source/schema check. `DONE` alone is not proof. If checking requires Main to redo the work, the unit is not a suitable opportunistic choice. Account for nonzero public exit or unresolved release before claiming completion.

A busy/unavailable service or failed, ambiguous or incomplete result returns control to the normal native/Main path under the handoff contract. Do not loop on availability, force reclaim, create a second instance, or repeat the objective with altered prompts/profiles. Existing resource leases and active-consumer protection remain authoritative; do not change another consumer's service, data or profile for this unit.

Reuse this task's service across successive units and immediately continuing goal turns. Before a normal final response, goal completion/cancellation/block, or open-ended wait, end this task's calls and release only its own instance through the configured owner-checked operation using the recorded instance identity or owner token. Active-consumer protection may defer release; never stop a borrowed or replaced service. A documented stop-after option may request the same owned cleanup for a final isolated call. Report unresolved release. After abrupt interruption, reconcile the recorded identity; host-exit cleanup is a fallback, not proof of turn cleanup. If no safe release contract exists, do not start a temporary service.

## Report only supported effects

Use current [price evidence](references/luna-lane.md#price-evidence) only when needed to compare costs. Compare qualified outcomes and total handoff/review/rework cost, not nominal price alone; raw token reduction and monetary savings are separate claims. A published unit price alone does not establish completed-work savings or a mandatory fallback.

Distinguish skill selection, successful dispatch, accepted work, and measured savings. Use existing results/logs when available; account for Main preparation/review/takeover and worker usage together, with latency separately. Do not double-count cumulative usage events or token subcategories. A successful example proves that path only. For invocation audits, choose the activity window and task sample independently of dispatch success; include non-dispatch, blocked and genuinely trivial cases. Separate new workers, follow-up work and coordination messages, and state the observation window and denominator. All-turn frequency is not the share of eligible work delegated; tool calls alone do not prove automatic skill selection. Do not target a call quota. Without comparable complete evidence, report token/cost savings and automatic invocation rate as unmeasured.
